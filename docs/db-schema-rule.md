# DB 스키마 관리 규칙

## 결론부터

**"서버 담당자가 SSH로 붙어서 스키마를 고친다"는 방식은 권장하지 않습니다.**
담당자를 한 명 정해도, 그 사람이 EC2에 직접 SSH로 붙어서 즉흥적으로 `ALTER TABLE`을 치는 방식이라면
근본적인 문제(코드 리뷰 없이 스키마가 바뀜, git 이력에 안 남음)가 그대로 남습니다.

## 왜 안 되나

- EC2에 SSH로 붙는 건 키만 있으면 누구나, 여러 명이 동시에 가능합니다. "담당자만 접속한다"는 규칙이
  시스템적으로 강제되지 않고, 결국 사람 기억에 의존하게 됩니다.
- 담당자가 SSH로 직접 `ALTER TABLE`을 실행하면, 그 변경 내용이 `backend/src/main/resources/schema.sql`
  (git으로 관리되는 정본)에는 자동으로 반영되지 않습니다.
- 그러면 "실제 운영 DB 구조"와 "git에 커밋된 schema.sql"이 서로 달라지고, 이후 로컬 개발 환경을 새로
  세팅하거나 다른 팀원이 `schema.sql`로 DB를 새로 만들면 그 수동 변경분이 통째로 빠진 채 재현됩니다.
- 리뷰 없이 스키마가 바뀌므로, 다른 팀원이 "왜 이 컬럼이 생겼지/사라졌지"를 git 이력에서 추적할 수 없습니다.

## 권장 워크플로우

1. 스키마 변경이 필요한 기능을 개발하는 사람이 **자기 feature 브랜치에서 `schema.sql`을 직접 수정**합니다.
2. 커밋 후 GitLab에 **MR을 올려 팀 리뷰**를 받습니다. (일반 코드 변경과 동일한 절차)
3. `develop`에 머지된 뒤, **그 MR에 적힌 SQL 그대로** EC2의 실제 DB에 반영합니다.
   - 이때 "누가 실행하느냐"는 정해도 되지만(예: 서버 담당자), 실행 내용은 항상 머지된 `schema.sql`의
     diff와 100% 동일해야 합니다 — SSH 세션에서 즉석으로 새로 생각해낸 SQL을 치면 안 됩니다.
4. 각자 로컬 개발 환경(docker mysql 컨테이너)도 같은 내용으로 맞춥니다.
   - 컨테이너를 새로 만들면 `schema.sql`이 자동 반영되지만, 이미 떠 있는 컨테이너는 `docker-entrypoint-initdb.d`가
     재실행되지 않으므로 **그 MR에 있는 것과 동일한 `ALTER TABLE`을 로컬에서도 각자 한 번씩 실행**해야 합니다.

## 요약

> 정본은 항상 git의 `schema.sql`입니다. EC2 DB는 그 정본을 "실행한 결과"일 뿐, 누군가 SSH로 붙어서
> 직접 결정하는 곳이 아닙니다. "누가 반영 작업을 하느냐"는 역할 분담일 뿐이고, "무엇을 바꾸느냐"는
> 항상 MR 리뷰를 거쳐야 합니다.
